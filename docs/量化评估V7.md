## 二、V7 新发现

### 🟠 R17. `refresh_fundamental_pit_incremental` 不更新存量码的新季报（R15 的实质失效）

`quant/data/fundamental_pit.py:refresh_fundamental_pit_incremental`：
```
done = codes_in_pit_table()              # 表中有任意行的码集合
pending = [c for c in codes if c not in done]   # 仅"表里完全没有"的码
```
`fetch_financial_pit_for_code` 本会重拉该码**全部历史**（start_year=2018）并 `write_fundamental_pit` 按 `(code, report_date)` upsert——能力上是能更新存量码新季报的。但 `pending` 过滤把存量码整体排除，**披露季刷新实际只补新上市码**。

**后果**：
- 首次 `build_fundamental_pit` 全量构建后，存量公司的 TTM **冻结在那一刻**；之后每个披露季（新 Q1/H1/Q3/年报公告）的增量**永不入表**（除非手动重跑全量 `build_fundamental_pit`）。
- 随时间推移，存量码 value 因子用越来越旧的 TTM → 时效性持续下降。**PIT 安全（不前视，只是过期）**，但 value 因子质量随时间衰减。
- `--force-fundamental-pit` 也救不了——它仅强制触发同一个 incremental，仍跳过存量码。

**修复路径**：把"刷新判定"从"码是否在表"改为"码的最新 report_date 是否早于该码最新已披露报告期"。最简实现：披露季刷新时 `pending = 全部 codes`（限流分批），靠 `write_fundamental_pit` 的 `(code, report_date) keep="last"` upsert 幂等去重；或维护 `last_fetched_report_date` 列只拉增量。配合 `limit`/`sleep` 控制单日拉取量。

### 🟢 R18. H1（8-31 截止）披露窗口未覆盖 8 月
`should_refresh_fundamental_pit` 仅 5 月全月 + 9/11 月前 15 日。H1 报告 8 月大量公告，但 8 月不触发 → 8 月下旬新 H1 数据不入表，要等 9 月 1 日。**轻微过期**（保守、PIT 安全）。建议加 8 月后半月到窗口。

### 🟢 R19. 5 月全月每日重复触发（浪费但无害）
`should_refresh` 对 5 月任意日返回 True → `update_daily` 每天都跑一次 incremental（且因 R17 只补新码，多数日空跑）。配合 R17 修复后改为"按需"或加 last-run 记录去重。

### 🟢 R20. `fundamentals.py` 残留死代码
`write_fundamentals_snapshot` 函数定义仍在（无调用方）。R14 删了调用未删定义。建议删 `fundamentals.py` 整文件或标注废弃，避免日后误用重启 spot 双源。

## 六、结论

R14 把 V6 最关心的 train-serve skew 根因（spot fundamentals 回退）彻底铲除，value 因子实现真正单源、live=回测；R16 死分支清理到位。**代码层面的结构性硬伤（前视/OOS 泄漏/非 TTM/双源/MVO/性能）至此全部清零，训练-实盘一致性从 B+ 升 A-。** 唯一新发现 R17 是 R15 运维闭环的"最后一公里"没接通：披露季刷新机制建好了，但 `pending` 过滤逻辑使其实际只补新上市码、不更新存量码新季报——fundamental_pit 会随时间冻结过期（PIT 安全但失效）。修掉 R17（一行过滤逻辑改动 + 限流）即闭合运维闭环。

**阶段判定**：GoldQuant 代码层已完成"可上小资金纸面/实盘验证"的全部前置条件，仅剩 R17 一处运维逻辑 bug 与 R18/R19/R20 几处打磨。**强烈建议下一步停止改代码、转跑真实 OOS 数据验证**——七轮评估累计已识别并修复约 20 项问题，但全部基于静态核验，真实回测绩效（NW-Sharpe、value IC、容量曲线）始终未产出。继续在代码层深挖的边际收益已低于跑一次端到端验证的边际收益；用数据证伪/证实才是当前最高 ROI 的动作。
