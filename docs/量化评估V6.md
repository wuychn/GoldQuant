## 一、V5 残留核验

### R11 亏损口径 ✅
`compute_ttm_eps` 移除 `ttm>0` 守卫，`return float(ttm)`（含负值）；`metrics_as_of` 改为：恒置 `ep_ttm = ttm_eps / px`（带符号，亏损为负 EP 排到弱价值端），仅 `ttm_eps>0` 时才置 `pe_ttm`。value 因子不再系统性剔除亏损股。✅

### R13 正则 ✅
末条危险规则 `.*?(20\d{2})年报` 改为 `(20\d{2})年(?!半).*?年报`（负向先行排除"半年报"误命）+ `(20\d{2})年报$` 行尾锚定。跨年误命风险消除。✅

### R7 上市日 ✅
`listing.py` 重构为 `resolve_listing_map`（parquet 基底 → AKShare IPO → jbxx → daily 首条，优先级递增）+ `listing_days_as_of/listing_days_map` 统一入口；`universe.py:55-57` `_listing_days_map` 调 `listing_days_map`，PIT 上市日表真正接入 universe 过滤。✅

### R12 维持
不足 4 季线性年化 `sum(qs)*(4/len(qs))`，文档自陈近似，仅影响次新股覆盖初期。🟢 维持。

## 二、全盘审计新发现（跨模块，前几轮漏掉）

### 🟠 R14. value 因子双源口径不一致（轻度 train-serve skew）

`panel_builder._inject_snapshot_factors`（`quant/factors/panel_builder.py:230`）仍调旧的 `read_fundamentals_snapshot(d)`，并用 `r.raw.setdefault("ep_ttm", 1.0/pe)` 把 **spot-based PE/PB**（vendor 当前值，`factor_capture.capture_fundamentals` 从 `stock_zh_a_spot_em` 的"市盈/市净"列取）作为 **fundamental_pit 缺失时的回退**：

- d 循环里 `metrics_as_of` 已用 fundamental_pit 的 TTM ep_ttm 写入 `bars.extras` → 因子函数算出 `raw["ep_ttm"]`。
- 后处理 `_inject_snapshot_factors` 用 `setdefault`：若 `raw["ep_ttm"]` 已存在（TTM 已覆盖）则不覆盖；**若 fundamental_pit 无该码/日数据，则回退到 vendor spot PE**。

**问题**：
1. **截面口径混用**——同一评估日里，fundamental_pit 覆盖的码用"我们算的滚动 4Q TTM"，未覆盖的码用"vendor spot 当前 PE"。两种 eps 定义/TTM 窗口不同，横截面不可比，削弱 value 因子排序质量。
2. **train-serve skew**——历史回测：spot 回退为空（历史无 spot 快照，`capture_fundamentals` 对 OHLCV 写不出 PE），所以**历史是纯 TTM**；live 今日：spot 快照由 `update_daily` 第 8 步写入，fundamental_pit 若未及时刷新则 spot 回退生效——**live 与回测的 value 因子构造口径不同**。
3. `roe`/`rev_yoy` 同理双源。

**修复路径**：确立 fundamental_pit 为唯一基本面来源，删除 `_inject_snapshot_factors` 里 fundamental 的 `setdefault` 回退分支与 `capture_fundamentals`/`write_fundamentals_snapshot` 的 spot 路径（hot/flow/theme 的 snapshot 回退可保留，因其本就是 snapshot 设计）。这样 value 因子口径单一、live=回测。需要先确保 fundamental_pit 全码覆盖（见 R15）。

### 🟠 R15. fundamental_pit 不在 update_daily 自动刷新（运维缺口）

`scripts/data/update_daily.py` 第 8 步 `capture_all_factor_snapshots` 只写 hot/flow/**spot fundamentals**/theme 四类快照，**不刷新 `fundamental_pit`**。fundamental_pit 仅由手动 `scripts/data/build_fundamental_pit` 构建，且无调度。

- 财报每季度披露一次，理论日更无必要；但**报告披露季结束后无自动触发** → TTM 滞后 → R14 的 spot 回退比例上升 → 加剧 train-serve skew 与截面口径混用。
- `backfill_factor_snapshots.py` 仍调 `capture_fundamentals`（写空 spot 快照）而非 `build_fundamental_pit`，回填脚本与真实基本面源脱节，属历史遗留 cruft。

**修复路径**：报告披露季（4/8/10 月末 + 次年 4 月末）后自动/半自动触发 `build_fundamental_pit --resume`；`update_daily` 第 8 步去掉对 spot fundamentals 的依赖（配合 R14 删除该路径）。

### 🟢 R16. `backfill_factor_snapshots` 与基本面源脱节（R14/R15 的表现）
该脚本对历史日期调 `capture_fundamentals(d, day)`（OHLCV），产出空——已无实际作用（历史基本面应走 `build_fundamental_pit`）。属死代码，建议删除其 fundamentals 分支或整体由 `build_fundamental_pit` 取代。

## 六、结论

V5 残留 R11/R13/R7 全部闭合，R12 维持。全盘审计确认前几轮结构性硬伤（前视、OOS 泄漏、非 TTM、MVO、性能）均已清零，训练-实盘 alpha 路径一致、universe/权重/成本均单一来源。**新发现集中在"基本面数据源未完全收敛到 fundamental_pit"这一集成问题**：`_inject_snapshot_factors` 保留的 spot fundamentals 回退（R14）与 `update_daily` 不刷新 fundamental_pit（R15）叠加，构成 value 因子的轻度 train-serve skew 与截面口径混用。

**阶段判定**：代码层面已无阻断"回测可信"的硬伤，GoldQuant 处于"**最后收敛数据源 + 跑真实 OOS 验证**"的收尾阶段。R14/R15 是把基本面从"双源带回退"收敛为"单源 fundamental_pit"的最后一步，做完即实现真正意义的 train-serve 一致。其后重心必须转向数据验证——当前所有评估均基于代码静态核验，**真实 OOS 绩效（NW-Sharpe、value IC、容量曲线）尚未跑出**，这是从"代码可信"到"策略可信"的临门一脚，建议尽快执行而非继续改代码。
